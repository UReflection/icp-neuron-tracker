## `--help` is the reference

Every flag, argument and default is generated by `clap` from the command definitions in
`src/main.rs`. It cannot drift from the binary:

```bash
icp-neuron-tracker --help
icp-neuron-tracker <command> --help
```

**This guide does not restate flags.** It covers only what `--help` cannot: file formats,
data hazards, where things live on disk, and how to read output that is easy to misread.
Every example below was produced by running the binary on the date above.

## CSV import: two formats work

The parser accepts two shapes and picks between them by looking for an `age_bonus_multiplier`
column in the header.

### Format A — full columns

Nine columns, everything stated explicitly. Use this one unless you have a reason not to.

```csv
neuron_id,snapshot_date,stake_e8s,staked_maturity_e8s,available_maturity_e8s,voting_power,dissolve_delay_seconds,age_seconds,created_timestamp_seconds
10000000000000000001,2026-01-05,100000000000,25000000000,0,300000000000,252460800,126230400,1600000000
```

### Format B — metadata comments plus `age_bonus_multiplier`

Fewer columns; dissolve delay, age and creation date come from a `#` metadata line instead.
One metadata line per neuron is **required** — an unmatched `neuron_id` is an error, not a
default.

```csv
# neuron_id: 10000000000000000001, created_date: 2021-05-17, dissolve_delay_years: 8
neuron_id,snapshot_date,stake_e8s,staked_maturity_e8s,available_maturity_e8s,voting_power,age_bonus_multiplier
10000000000000000001,2026-01-07,1000.00000000,250.00000000,0,300000000000,1.25
```

Age is derived by inverting `age_bonus_multiplier`, so it is capped at the four-year maximum
that bonus can express. A neuron older than four years imports as exactly four years.

### The format older docs described does not exist

Documentation before 2026-08-05 described a "simplified format (recommended)" with columns
`neuron_id,date,stake,staked_maturity,maturity,...`. **No such format is implemented.** The
parser rejects it:

```
Import failed: Missing required column 'snapshot_date' in CSV header.
```

If you have files in that shape, rename `date` to `snapshot_date` and the value columns to
`stake_e8s`, `staked_maturity_e8s` and `available_maturity_e8s`.

## The `stake_e8s` trailing-`.0` hazard

**Read this before importing anything that came from a spreadsheet.**

Despite the column name, `stake_e8s` accepts *both* raw e8s integers and decimal ICP, and
tells them apart by the presence of a decimal point:

| CSV value | Interpreted as | Stored |
|---|---|---|
| `100` | 100 e8s | **0.00000100 ICP** |
| `100.0` | 100 ICP | **100.00000000 ICP** |

**A trailing `.0` is worth a factor of 100,000,000.** There is no warning. The same applies to
`staked_maturity_e8s` and `available_maturity_e8s`.

This matters because spreadsheets strip trailing zeros: a cell holding `458.0` ICP, exported
as `458`, becomes 0.00000458 ICP on import.

**Import with `--dry-run` first**, then confirm the figures with `report summary`. A value that
lost its decimal point is absurdly small rather than subtly wrong, so it is easy to spot.

## What `export` actually emits

Always **Format A** — raw e8s integers — regardless of which format the data was imported in.
Since **format version 1.1** there are ten columns: the nine of format 1.0 plus
`retrieved_timestamp_seconds`.

```csv
# ICP Neuron Tracker - Historical Data Export
# Export Date: 2026-08-05 15:11:28
# Total Records: 5
# Format Version: 1.1
#
neuron_id,snapshot_date,stake_e8s,staked_maturity_e8s,available_maturity_e8s,voting_power,dissolve_delay_seconds,age_seconds,created_timestamp_seconds,retrieved_timestamp_seconds
```

Older docs claimed exports used ICP units with `# Neurons:` and `# Date Range:` headers. They
do not.

### `retrieved_timestamp_seconds` — the provenance column

This is when each snapshot was **observed**, and it is the only thing distinguishing rows
collected automatically from rows brought in by bulk CSV import. Do not confuse it with
`created_timestamp_seconds`, which is when the neuron was created on chain.

Format 1.0 omitted it, so re-importing a backup restamped every row with the import time and
silently relabelled years of automated collection as observed today. It is now exported and
preserved on import. Files written by 1.0 remain importable; those rows get the import time,
because their observation time was never recorded anywhere.

### Two fields are inferred, not round-tripped

`state` and `auto_stake_enabled` are not exported. On import they are derived:

| Field | Inference |
|---|---|
| `state` | `Locked` if `dissolve_delay_seconds > 0`, otherwise `Dissolved` |
| `auto_stake_enabled` | `true` if `staked_maturity_e8s > 0` |

A round-trip preserves them only where the inference is right. A **dissolving** neuron has a
non-zero dissolve delay and so returns as `Locked`; a locked neuron that has never accrued
staked maturity returns with auto-stake off. Everything measured — stake, maturity, staked
maturity, voting power, ages, both timestamps — round-trips exactly.

**Export then import round-trips exactly** for the measured columns. Re-importing an export
reports every row as a duplicate and changes nothing, which is the intended result.

## `project --offline` and the staleness banner

`project` needs one thing from the network: your *current* portfolio value. Everything else —
reward history, percentiles, data quality — comes from the local database.

- `--offline` skips the network and uses the newest stored snapshot.
- Without the flag, a live query is attempted and **falls back to stored data** if it fails.

Either way you get a banner. It is never suppressed:

```
============================================================
OFFLINE PROJECTION - using stored data
============================================================

Portfolio value source:  newest stored snapshot (not a live query)
Current portfolio value: 1250.0000 ICP
Data retrieved:          2026-01-07 20:05:05 UTC
Age of data:             209 days old
```

**Read the direction of the error.** Stake and maturity grow between snapshots, so a stale
portfolio value **understates** what you hold. That widens the apparent gap to your target, so
**the projected retirement date is later than reality, not earlier** — a conservative bound.
Track regularly and the gap closes; the banner's age figure tells you how far off you are.

## Where things live

**Config** — `config.toml` is looked up in the platform config directory first, then the
current working directory:

```
Linux    ~/.config/icp-neuron-tracker/config.toml
```

The path comes from the `directories` crate using `com / u-reflection / icp-neuron-tracker`,
so it differs on macOS and Windows. `icp-neuron-tracker identity info` prints the config it
actually loaded.

**Database** — wherever `tracking.history_file` in your config points. It is **not** implied by
the config directory. It may be a bare filename, in which case it resolves relative to your
current directory — so running the tool from two different places can silently create two
different databases. Prefer an absolute path.

**Identity** — wherever `identity.pem_file` points. Generated keys are written with `600`
permissions in SEC1 PEM format (`BEGIN EC PRIVATE KEY`).

`config.toml`, `*.pem`, `*.db` and `*.csv` are gitignored — never commit real neuron IDs or
keys. `project` does **not** write to your config; it reads it and leaves it byte-identical.

## Data quality grades

`project` prints one of five grades, defined in `src/domain/retirement.rs`:

| Grade | Threshold |
|---|---|
| Insufficient | < 7 days |
| Low | 7–29 days |
| Moderate | 30–89 days |
| Good | 90–179 days |
| Excellent | 180+ days |

**The grade does not control whether a projection runs.** It is a label on the history you
have, not a gate. This table previously marked "Insufficient" as the point at which a
projection is refused, which implied that clearing seven days would unblock `project`. It
does not — see [What `project` actually requires](#what-project-actually-requires) below.

**The grade counts distinct reward dates. It says nothing about recency.**

The query is `SELECT COUNT(DISTINCT reward_date) FROM daily_rewards`. A database holding three
years of history that has not been updated since January still grades **Excellent**, because
those days exist — they are simply all in the past. This is why an "Excellent" grade can sit
directly above a banner saying the data is 209 days old. Both statements are true; they
measure different things.

**Read the grade as depth of history and the banner as freshness**; trust a projection only
when both are satisfied. Note also that the grade describes the whole table, while the
projection's percentiles are drawn from a 90-day lookback only — see below.

## What `project` actually requires

Risk scenarios need **11 populated non-overlapping 7-day windows within a 90-day lookback**.
From an empty database that is roughly **11 weeks of daily tracking**, and it is the real
gate — the data-quality grade above is a label, not a threshold.

A window is *populated* only when every day in it is covered by a reward row. A window with
any uncovered day is *unobservable* and is left out of the sample rather than counted as
zero, because a week nothing was recorded for is not a week that paid nothing. Treating the
two as the same drives the 10th percentile to zero and projects "never" from missing data.
A genuine zero-reward week — rows present, rewards actually zero — **is** populated and
counts.

This is also why a collection gap does not simply resolve itself on the next run. A reward
row whose `days_elapsed` exceeds one window is an accrual gap: it records a real total over a
span it gives no within-span detail for, so it funds no window and the weeks it covers stay
unobservable. A 211-day gap removes twelve windows from a 90-day lookback and `project` will
refuse until daily tracking has rebuilt them.

When the floor is not met, the error reports how many windows are populated, how many were
excluded as unobservable, how many were genuine zero-reward weeks, and names the gap
responsible. It is telling you what it does not have, not that your neurons stopped earning.

Percentile bands come from **non-overlapping** windows. Earlier versions expanded the most
recent 30 reward dates into trailing 7-day rates, so one day's reward could appear in up to
seven samples and a single strong week could populate the top decile with copies of itself.
